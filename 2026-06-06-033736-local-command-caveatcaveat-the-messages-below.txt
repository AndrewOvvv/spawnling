  ---
  По Kubernetes:

  Проблема в том, что K8s — это инфраструктура, которую нужно иметь заранее. Для
   домашнего игрока это огромный барьер входа. Поэтому я предлагаю такую модель:

  daemon
    └── Runtime (interface)
          ├── ProcessBackend   ← default, работает везде
          └── K8sBackend       ← опционально, для тех у кого уже есть кластер

  Process backend запускает серверы как дочерние JVM-процессы — никаких
  зависимостей. K8s backend можно добавить позже, не меняя остальной код, потому
   что интерфейс уже заложен. Вопрос только в том — делаем ли мы K8s backend в
  v1 или оставляем на потом.

  По мониторингу в K8s (твой вопрос):

  Если всё же делаем K8s backend — рекомендую центральный демон без sidecar.
  Демон сам идёт к K8s API за метриками CPU/RAM, читает логи через client-go
  (аналог kubectl logs -f), и подключается к серверу по RCON для статуса
  игроков. Sidecar нужен только если нам нужны JVM-internals — нам не нужны.

  По протоколу CLI ↔ Daemon:

  gRPC даёт стриминг логов из коробки и один .proto файл как контракт. REST +
  SSE тоже работает, но сложнее для интерактивной консоли (attach). Для будущего
   web UI оба варианта одинаково готовы — grpc-gateway vs обычный HTTP сервер.

     Architecture Plan: Spawnling

     Context

     Designing the core architecture before writing any code. User confirmed:
     - Process backend as the only v1 backend (K8s deferred to v2)
     - gRPC over unix socket for CLI ↔ Daemon communication
     - K8s monitoring approach discussed: central daemon (no sidecar) via K8s
     API + RCON

     ---
     System Overview

     ---
     Components

     Runtime Interface

     type Runtime interface {
         Create(ctx context.Context, spec InstanceSpec) error
         Start(ctx context.Context, name string) error
         Stop(ctx context.Context, name string) error
         Delete(ctx context.Context, name string) error
         Logs(ctx context.Context, name string) (io.ReadCloser, error)
         Exec(ctx context.Context, name string, cmd string) error
         Stats(ctx context.Context, name string) (Stats, error)
     }

     Interface is defined in v1; only ProcessBackend implemented.
     K8sBackend plugs in later without touching other components.

     ProcessBackend

     Each server = child JVM process (os/exec).

     daemon
       ├── os/exec → JVM process (stdin/stdout/stderr pipes attached)
       ├── stdout/stderr pipe → log ring buffer → streamed to CLI via gRPC
       ├── stdin pipe → send commands to running server
       ├── RCON (TCP, localhost) → query player list, TPS
       └── /proc/<pid>/stat (Linux) / runtime APIs → CPU%, RSS

     Auto-restart: goroutine watches cmd.Wait(), respawns if crash-restart
     enabled.

     Monitor Service

     Runs inside the daemon, polls each running instance:
     - Process alive check (every 5s)
     - RCON query for player list (every 10s)
     - /proc stats for CPU/RAM (every 5s)
     - Aggregates into in-memory state, pushed to subscribers via gRPC streams

     Instance Manager

     - Stores instance config as JSON: ~/.spawnling/instances/<name>/config.json
     - Downloads server JARs from official sources (Paper API, Mojang manifest)
     - Manages server.properties and JVM args
     - Config survives daemon restarts

     Tunnel Service

     - Wraps playit-cli agent binary (downloaded on first use, cached)
     - One tunnel process per server instance (not a daemon-global process)
     - Exposes tunnel address via gRPC to CLI

     gRPC API

     Single .proto file defines all operations:
     - InstanceService — CRUD + start/stop/status
     - LogService — streaming logs (server-side stream)
     - ConsoleService — bidirectional stream for interactive console
     - TunnelService — start/stop/status tunnel
     - BackupService — trigger/list/restore backups

     Transport: unix socket /tmp/spawnling.sock (localhost only, NFR-3.1).
     For future web UI: add grpc-gateway alongside the socket (HTTP/JSON on
     :7420).

     Repository Structure

     spawnling/
     ├── cmd/
     │   ├── spawnling/        ← CLI entrypoint (cobra)
     │   └── spawnlingd/       ← daemon entrypoint

     ---
     K8s Backend (v2, deferred)

     When implemented: central daemon approach, no sidecar.
     - Daemon talks to K8s API via client-go
     - Metrics via Kubernetes Metrics Server API
     - Logs via client-go log streaming (equivalent to kubectl logs -f)
     - Commands via RCON TCP (exposed as a K8s Service)
     - Each server = Deployment + Service; daemon manages them via CRDs or
     labels

      mock_config_store.go      ← сгенерировано

  Два открытых вопроса перед тем как фиксировать в архитектурный документ:

  1. Инструмент генерации моков:
  - mockery — проще, //go:generate mockery --name=RuntimeBackend, конфиг в
  .mockery.yaml
  - gomock + mockgen — мощнее (verify-вызовы, порядок вызовов), но больше
  бойлерплейта в тестах

  2. Wiring (где собираются все зависимости):
  - Ручной DI в cmd/spawnlingd/main.go — явно, без магии, легко читать
  - Wire (google/wire) — кодогенерация графа зависимостей, оправдано при большом
   количестве модулей

  Мои рекомендации: mockery + ручной DI. Просто, предсказуемо, без лишних
  инструментов в цепочке сборки. Что думаешь?

⏺ Отвечу на твой вопрос, а потом завершу тайди и коммит.

  ---
  src/ в Go — антипаттерн. Вот почему:

  Это наследие старого GOPATH-мира ($GOPATH/src/...). Начиная с Go Modules
  (1.11) — никто так не делает. Если перенести в src/, импорты станут:

  // вместо
  import "github.com/AndrewOvvv/spawnling/internal/instance"

  // получим
  import "github.com/AndrewOvvv/spawnling/src/internal/instance"

  Это не-идиоматично, и любой Go-разработчик при первом взгляде на проект
  удивится.

  Текущая структура уже считается чистой и стандартной в Go-сообществе — cmd/,
  internal/, proto/ на корне рядом с go.mod. Нас тут не мешают ни скрипты, ни
  конфиги, ни медиафайлы, так что причин для src/ нет.
